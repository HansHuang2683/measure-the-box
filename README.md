# 📦 FBA 装箱优化工具

这是一个面向亚马逊 FBA 场景的装箱与补货计算器。它不是简单按体积做加减法，而是同时考虑了 SKU 尺寸、包装类型、箱体内外尺寸、摆放朝向、空腔支撑、软包压缩估算，以及 5cm 倍数常规箱型遍历。

这个项目是纯前端应用，直接打开 `index.html` 就能运行，不需要单独部署后端。

## 这个项目能做什么

- 录入 SKU 的名称、长宽高、数量、包装类型和软包公差。
- 选择标准箱型或自定义箱型。
- 自动生成混装分组，并计算每箱能装多少件。
- 用 3D 视图显示真实摆放结果。
- 在当前混装方案基础上做剩余空间补货推荐。
- 遍历 5cm 倍数的常规箱型，帮助判断是否该换箱。
- 导入和导出 xlsx 数据。

## 怎么运行

### 第 1 步：打开项目

直接双击 `index.html` 就可以运行。页面会在浏览器里加载算法、数据录入区和 3D 视图。

如果你想避免浏览器对本地文件的限制，也可以用一个简单的静态服务器打开整个目录。

### 第 2 步：先看页面结构

页面从上到下大致分成几块：

- SKU 录入区
- 箱子类型区
- 混装组配置区
- 3D 可视化区
- 剩余空间补货推荐区
- 5cm 倍数箱型遍历区

你可以把它理解成“先录数据，再算方案，再看结果，再做补货对比”。

## 新手一步一步怎么用

### 第 1 步：录入 SKU

每一行 SKU 需要填：

- 名称
- 长
- 宽
- 高
- 数量
- 包装类型
- 软包公差

系统在这一步不会直接装箱，只是先把原始数据标准化。

如果是硬包装，系统通常直接按原始尺寸参与计算。

如果是软包装，系统会先把“可压缩性”算进去。逻辑大致是：

```text
软包有公差时：
effective = original × (1 - tolerance)^(1/3)

软包没有填写公差时：
effective = original - 2cm / 每边
```

这就是为什么同样大小的软包，系统会比硬包更愿意把它放进某些空位里。

### 第 2 步：选择箱子类型

箱子有两种来源：

- 系统里已有的标准箱
- 你自己新增的自定义箱

每个箱子都有外尺寸和内尺寸。真正参与计算的是内尺寸，因为纸箱壁厚会占空间。

如果箱子的外尺寸是 `60×60×45`，壁厚是 `1cm`，那内尺寸会变成：

```text
内长 = 60 - 1×2 = 58
内宽 = 60 - 1×2 = 58
内高 = 45 - 1×2 = 43
```

也就是说，系统判断“能不能放下”，看的不是外箱，而是内箱。

### 第 3 步：点“自动分配方案”

这一步是主算法开始工作的地方。

系统会先把 SKU 按硬包、软包分开看，再去尝试不同的混装组合。它不是只挑一个大概能装的箱子，而是会枚举候选箱型、候选箱数和每箱分配方式，再挑出评分最高、且真正能摆进去的方案。

当前版本里有一个很重要的规则：

- 只接受真实完整摆放的方案
- 估算能装但实际有溢出的方案，不算最终结果

对应到代码层面，自动混装要同时满足：

```text
verifiedFit == true
overflowItems 为空
实际摆放件数 == 每箱应放件数
```

这也是为了避免“界面看起来利用率很高，但 3D 图里有件产品飘在箱外面”的情况。

### 第 4 步：看 3D 可视化

3D 视图显示的是系统算出来的真实摆放结果。

你看到的东西可以这样理解：

- 蓝色框：箱体
- 彩色实体块：已放入的 SKU
- 半透明绿色区域：可识别的空腔
- 箱外悬浮的块：表示该件当前方案下没能放进去

如果你切换空腔显示，能更直观看到哪些空间是真的能继续利用，哪些只是视觉上“有空”，但实际上已经被切碎了。

### 第 5 步：看“剩余空间补货推荐”

这一步不是重新换箱，而是保持当前箱子和当前混装结果不变，只继续想办法把箱内剩余空间利用起来。

系统会先从当前 3D 布局里提取空腔，再把候选小件放进去。

候选来源包含：

- 软包 SKU
- 没有分配完的 SKU
- 体积很小的硬包 SKU

补货推荐会优先考虑：

- 低位空腔
- 贴边空腔
- 体积更大的有效空腔
- 支撑更好的位置

软包在补货阶段会用更大胆的压缩估算，这是为了尽量利用剩余空间，但最后仍然要通过放置校验。

### 第 6 步：看 5cm 倍数箱型遍历

这一步是给“要不要换更合适的常规箱”看的。

系统会遍历一批 5cm 倍数的标准箱型，比如：

- `55×55×50`
- `60×55×50`
- `60×60×45`
- `60×60×50`

每一行都会重新计算：

- 当前利用率
- 补货后利用率
- 每箱还能补多少件
- 推荐的补货结构
- 箱体相对变化

现在表格里还加了 `3D 预览` 按钮。点一下，就能直接看这个候选箱型的 3D 结果，不用手算。

## 计算逻辑怎么走

### 1. 单 SKU 算法

单 SKU 的算法会枚举 6 个朝向，然后分别算每个方向能放多少件。

核心公式是：

```text
每轴件数 = floor((箱内尺寸 - 间隙) / (产品尺寸 + 间隙))
每箱件数 = 长向件数 × 宽向件数 × 高向件数
```

系统会在所有朝向里选件数最多的，如果件数一样，就选利用率更高的那个。

### 2. 混装算法

混装不是简单把所有 SKU 混在一起算体积，而是先做候选搜索，再做严格验证。

算法大概是：

1. 生成候选箱型
2. 尝试不同箱数
3. 尝试不同每箱分配方式
4. 计算利用率和剩余件数
5. 用 3D 布局做真实验证
6. 只保留完全能装进去的方案

简单说，它是“先广搜，再严格验收”。

当前自动分配还有一个现实策略：

- 只有硬包或只有软包时，直接在全部 SKU 上搜索
- 硬包和软包同时存在时，先优先保证硬包方案，再用全部 SKU 继续填充
- 如果还有剩余，再尝试生成第二组混装

### 3. 剩余空间补货推荐

补货推荐会把当前混装结果切成空腔，然后在空腔里试放候选小件。

放置时会检查：

- 是否越界
- 是否和已有产品重叠
- 是否有足够支撑
- 是否满足软包或硬包的摆放规则

支撑阈值目前大致是：

- 硬包：`0.85`
- 软包：`0.50`

这就是为什么有时你“目视觉得能塞进去”，系统却不放。很多看起来空的地方，其实已经被切成了很窄的碎片，或者上方没有足够支撑，系统不会把它当成安全可用空间。

### 4. 为什么看起来有空位，系统却不放

常见原因有这些：

- 空位太窄，小于候选产品最小边
- 空位在上层，但支撑不足
- 空间已经被切成碎片，无法形成完整矩形
- 某个方向刚好卡边界，被小数误差影响
- 方案只是估算可行，但没有通过真实 3D 验证

当前版本已经把“估算但不完整”的方案排除了，所以结果会更稳，不会再出现箱外浮件。

## 举个例子

### 示例 1：单 SKU 怎么算

假设：

```text
箱内尺寸：58 × 58 × 43 cm
产品尺寸：43.2 × 33 × 8.5 cm
```

系统会先枚举这个产品的 6 个朝向，然后算每个朝向能放几件。

如果按 `43.2 × 33 × 8.5` 这个朝向计算，公式就是：

```text
长向 1 件 × 宽向 1 件 × 高向 6 件 = 6 件/箱
```

最后系统会在所有朝向里选最优解。

### 示例 2：混装 + 补货

以我现在这组测试数据为例：

- 当前方案：`60×60×45`
- 当前利用率：`69.5%`
- 补货后利用率：`83.9%`
- 每箱新增：`89 件`
- 推荐补货结构：Heavy `29/箱`、Single `30/箱`、Double `30/箱`

这说明当前箱子里的剩余空间不是“没有空间”，而是系统经过空腔判断和支撑校验后，找到了更适合继续塞进去的小件组合。

### 示例 3：5cm 倍数箱型遍历

假设当前箱型是 `60×60×45`，系统会继续测试周围的常规箱型，比如：

- `55×55×50`
- `60×55×50`
- `60×60×50`

每个候选箱都会重新算利用率和补货结果。

如果你点击某一行的 `3D 预览`，就会直接看到这个候选箱型在 3D 里的样子。

## 项目结构

```text
index.html              主页面
css/style.css           页面样式
js/config.js            常量与通用工具
js/algorithm.js         单 SKU 装箱算法
js/algorithm-mixed.js   混装算法与布局验证
js/algorithm-cavity.js  空腔吸附/低位补空算法
js/replenishment.js     剩余空间补货推荐
js/customBox.js         定制箱建议

js/renderer3d.js       Three.js 3D 渲染
js/ui.js               页面交互逻辑
js/xlsxHandler.js       xlsx 导入导出
```

## 技术栈

- 原生 JavaScript（ES6+）
- [Three.js](https://threejs.org/) r128
- [SheetJS](https://sheetjs.com/)

## 说明

- 这个项目的算法是启发式搜索，不是数学意义上的全局最优求解器。
- 软包的补货推荐是按压缩估算来的，适合先做方案判断，实际采购前仍建议打样确认。
- 3D 视图展示的是算法结果，不是示意图。
