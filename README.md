# 📦 FBA 装箱优化工具

这是一个面向亚马逊 FBA 场景的装箱与补货计算器。它不是简单按体积做加减法，而是同时考虑 SKU 尺寸、重量、包装类型、箱体内外尺寸、摆放朝向、软包塑形估算，以及已有箱型列表遍历。

核心装箱计算可以直接打开 `index.html` 预览；如果要使用登录、保存历史、读取历史等账号功能，必须通过后端服务访问 `http://localhost:8000/`。

## 这个项目能做什么

- 录入 SKU 的名称、长宽高、数量、单件重量、包装类型和软包公差。
- 选择标准箱型或自定义箱型。
- 自动生成混装分组，并计算每箱能装多少件。
- 用 3D 视图显示真实摆放结果。
- 在当前混装方案基础上做剩余空间补货推荐。
- 遍历第二步已有箱型列表，帮助判断是否该换箱。
- 导入和导出 xlsx 数据。

## 怎么运行

### 方式 A：只看本地计算

直接双击 `index.html` 就可以运行。页面会在浏览器里加载算法、数据录入区和 3D 视图。

这种方式适合快速测试装箱计算，但登录、保存历史、读取历史不可用。

### 方式 B：启用登录和历史记录

从项目根目录启动后端：

```powershell
cd backend
$env:SECRET_KEY="dev-secret-change-me"
python main.py
```

然后用浏览器打开：

```text
http://localhost:8000/
```

如果你使用 `uvicorn`，也可以这样启动：

```powershell
cd backend
$env:SECRET_KEY="dev-secret-change-me"
uvicorn main:app --host 0.0.0.0 --port 8000 --reload
```

`SECRET_KEY` 用于签发登录 token，正式使用时请换成更长的随机字符串。`CORS_ORIGINS` 可以按需配置允许访问的前端来源，默认已支持 `http://localhost:8000` 和 `http://127.0.0.1:8000`。

### 第 2 步：先看页面结构

页面从上到下大致分成几块：

- SKU 录入区
- 箱子类型区
- 混装组配置区
- 3D 可视化区
- 结果汇总区
- 剩余空间补货推荐区
- 已有箱型遍历区

你可以把它理解成“先录数据，再算方案，先看 3D 摆放，再看结果和补货对比”。

## 新手一步一步怎么用

### 第 1 步：录入 SKU

每一行 SKU 需要填：

- 名称
- 长
- 宽
- 高
- 数量
- 单件重量
- 包装类型
- 软包公差

系统在这一步不会直接装箱，只是先把原始数据标准化。

如果是硬包装，系统通常直接按原始尺寸参与计算。

硬盒彩盒在混装 3D 里默认按“平放”处理：长宽可以旋转，但高度保持产品原始高度。这样可以避免系统为了追求体积利用率，把硬盒彩盒竖起来摆成不符合实际操作的方案。

如果是软包装，系统会先把“可压缩性”算进去。逻辑大致是：

```text
软包有公差时：
effective = original × (1 - tolerance)^(1/3)

软包没有填写公差时：
effective = original - 2cm / 每边
```

这就是为什么同样大小的软包，系统会比硬包更愿意把它放进某些空位里。

### 第 2 步：选择箱子类型

箱子有两种来源：

- 系统里已有的标准箱
- 你自己新增的自定义箱

当箱型很多时，第二步的箱型列表默认折叠显示，只展示前几个箱型和总数量。点击“展开选择箱型”后，可以看到全部已添加箱型。

展开后每个箱型都有“使用”按钮。点击后，系统会把该箱型同步到当前正在查看的混装组；如果当前没有正在查看的 3D 箱子，则默认应用到第一个混装组。同步后第三步混装组的箱型下拉和 3D 视图都会刷新。

每个箱子都有外尺寸和内尺寸。真正参与计算的是内尺寸，因为纸箱壁厚会占空间。

如果箱子的外尺寸是 `60×60×45`，壁厚是 `1cm`，那内尺寸会变成：

```text
内长 = 60 - 1×2 = 58
内宽 = 60 - 1×2 = 58
内高 = 45 - 1×2 = 43
```

也就是说，系统判断“能不能放下”，看的不是外箱，而是内箱。

### 第 3 步：点“自动分配方案”

这一步是主算法开始工作的地方。

系统会先把 SKU 按硬包、软包分开看，再去尝试不同的混装组合。它不是只挑一个大概能装的箱子，而是会枚举候选箱型、候选箱数和每箱分配方式，再挑出评分最高、且真正能摆进去的方案。

第三步顶部可以先选择装箱模式，再点击“自动分配方案”：

- `真实安全装箱`：所有 SKU 都必须形成完整真实摆放，硬包和软包都不能靠估算吸收。
- `最少溢出装箱（软包塑形）`：硬包仍必须真实摆放；软包如果只剩少量未放入，可以按碎片空腔总体积和视觉空位做塑形吸收。

在 `真实安全装箱` 下，自动混装要同时满足：

```text
verifiedFit == true
overflowItems 为空
实际摆放件数 == 每箱应放件数
```

这也是为了避免“界面看起来利用率很高，但 3D 图里有件产品飘在箱外面”的情况。

在 `最少溢出装箱（软包塑形）` 下，系统允许少量软包以绿色块显示为“建议压入/塑形吸收”。硬包永远不进入这条分支，如果溢出的是硬包，该方案仍然失败。

自动分配完成后，混装组卡片还会检查第二步箱型列表里是否存在更合适的箱型。系统不会再临时生成 `5cm` 倍数箱，只会使用已经添加到箱子类型里的箱。点击“应用并查看3D”后，会自动把第三步的混装组箱型切换到推荐箱，并刷新 3D 模型。

自动分配会优先尝试 `5` 箱完整装完。只要已有箱型列表里存在可行的 `5` 箱方案，系统会优先选择 `5` 箱；只有 `5` 箱无法完整装完时，才继续考虑更多箱数。

### 第 4 步：看 3D 可视化

3D 视图显示的是系统算出来的摆放结果。当前界面只保留核心视图，避免把多种估算口径混在一起造成误解。

你看到的东西可以这样理解：

- 蓝色框：箱体
- 彩色实体块：已放入的 SKU
- 绿色实体块：最少溢出模式下，被建议压入或塑形吸收的软包
- 箱外悬浮的块：表示该件当前方案下没能放进去

绿色软包只会出现在“最少溢出装箱（软包塑形）”模式下。它保持原 SKU 尺寸，只允许平面旋转，不会被缩成小块，也不会把硬包当成可压缩物体。绿色块和蓝色块轻微重叠时，表示这件软包需要靠压入、塑形或挤压吸收；它是采购和装箱估算提示，不等于严格几何无重叠。

为了让界面更稳定，`空腔吸附`、`显示空腔`、`软包压缩估算`、`真实+软包估算` 等实验入口已经从界面隐藏。后续如果要恢复，会先重新定义清楚每个模式的验收标准。

### 第 5 步：看“剩余空间补货推荐”

这一步不是重新换箱，而是保持当前箱子和当前混装结果不变，只继续想办法把箱内剩余空间利用起来。

系统会先从当前 3D 布局里提取可用区域，再把候选小件放进去。

候选来源包含：

- 软包 SKU
- 没有分配完的 SKU
- 体积很小的硬包 SKU

补货推荐会优先考虑：

- 低位空腔
- 贴边空腔
- 体积更大的有效空腔
- 支撑更好的位置

软包在补货阶段可以使用更大胆的塑形估算，这是为了尽量利用剩余空间；硬包仍然必须通过真实放置校验。

### 第 6 步：看已有箱型遍历

这一步是给“要不要换更合适的常规箱”看的。

系统会遍历第二步箱子类型列表里的箱型，比如：

- `55×55×50`
- `60×55×50`
- `60×60×45`
- `60×60×50`

每一行都会重新计算：

- 当前利用率
- 补货后利用率
- 每箱还能补多少件
- 推荐的补货结构
- 箱体相对变化

现在表格里还加了 `3D 预览` 按钮。点一下，就能直接看这个候选箱型的 3D 结果，不用手算。

第三步的混装组卡片也会出现更合适的已有箱型建议。这个建议必须通过真实 3D 摆放验证，不会只按体积估算就推荐。

## 计算逻辑怎么走

### 1. 单 SKU 算法

单 SKU 的算法会枚举 6 个朝向，然后分别算每个方向能放多少件。

核心公式是：

```text
每轴件数 = floor((箱内尺寸 - 间隙) / (产品尺寸 + 间隙))
每箱件数 = 长向件数 × 宽向件数 × 高向件数
```

系统会在所有朝向里选件数最多的，如果件数一样，就选利用率更高的那个。

### 2. 混装算法

混装不是简单把所有 SKU 混在一起算体积，而是先做候选搜索，再做严格验证。

算法大概是：

1. 生成候选箱型
2. 尝试不同箱数
3. 尝试不同每箱分配方式
4. 计算利用率和剩余件数
5. 用 3D 布局做真实验证
6. 按当前装箱模式决定是否允许少量软包塑形吸收

简单说，它是“先广搜，再按模式验收”。真实安全装箱会严格要求全部 SKU 形成完整摆放；最少溢出装箱允许软包用绿色块表达压入/塑形吸收，但硬包仍然严格验证。

当前自动分配还有一个现实策略：

- 只有硬包或只有软包时，直接在全部 SKU 上搜索
- 硬包和软包同时存在时，先优先保证硬包方案，再用全部 SKU 继续填充
- 如果还有剩余，再尝试生成第二组混装

### 3. 剩余空间补货推荐

补货推荐会把当前混装结果切成可用区域，然后在其中试放候选小件。

放置时会检查：

- 是否越界
- 是否和已有产品重叠
- 是否有足够支撑
- 是否满足软包或硬包的摆放规则

支撑阈值目前大致是：

- 硬包：`0.85`
- 软包：`0.50`

这就是为什么有时你“目视觉得能塞进去”，系统却不放。很多看起来空的地方，其实已经被切成了很窄的碎片，或者上方没有足够支撑，系统不会把它当成安全可用空间。

### 4. 为什么看起来有空位，系统却不放

常见原因有这些：

- 空位太窄，小于候选产品最小边
- 空位在上层，但支撑不足
- 空间已经被切成碎片，无法形成完整矩形
- 某个方向刚好卡边界，被小数误差影响
- 方案只是估算可行，但没有通过真实 3D 验证

在 `真实安全装箱` 下，系统会把“估算但不完整”的方案排除掉，所以结果更稳，不会把箱外浮件当成已装入。

在 `最少溢出装箱（软包塑形）` 下，系统允许少量软包用绿色块显示为“可压入/可塑形吸收”。这类绿色块不参与硬包校验，也不代表严格几何无重叠。

## 举个例子

### 示例 1：单 SKU 怎么算

假设：

```text
箱内尺寸：58 × 58 × 43 cm
产品尺寸：43.2 × 33 × 8.5 cm
```

系统会先枚举这个产品的 6 个朝向，然后算每个朝向能放几件。

如果按 `43.2 × 33 × 8.5` 这个朝向计算，公式就是：

```text
长向 1 件 × 宽向 1 件 × 高向 6 件 = 6 件/箱
```

最后系统会在所有朝向里选最优解。

### 示例 2：混装 + 补货

以我现在这组测试数据为例：

- 当前方案：`60×60×45`
- 当前利用率：`69.5%`
- 补货后利用率：`83.9%`
- 每箱新增：`89 件`
- 推荐补货结构：Heavy `29/箱`、Single `30/箱`、Double `30/箱`

这说明当前箱子里的剩余空间不是“没有空间”，而是系统经过空腔判断和支撑校验后，找到了更适合继续塞进去的小件组合。

### 示例 3：已有箱型遍历

假设当前箱型是 `60×60×45`，系统会继续测试第二步箱型列表里的其他箱型，比如：

- `55×55×50`
- `60×55×50`
- `60×60×50`

每个候选箱都会重新算利用率和补货结果。

如果你点击某一行的 `3D 预览`，就会直接看到这个候选箱型在 3D 里的样子。

## 说明

- 这个项目的算法是启发式搜索，不是数学意义上的全局最优求解器。
- 软包塑形和补货推荐适合先做方案判断，实际采购前仍建议打样确认。
- 3D 视图展示的是算法结果，不是示意图。
